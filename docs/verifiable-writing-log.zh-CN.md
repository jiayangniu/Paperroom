# Paperroom 可校验写作日志

> **0.7.4 功能说明** · [打开本地验证页](verify.html)

投稿时，作者可以随论文附带一份写作日志。审稿人打开就能直观看到：作者怎么安排段落、采纳过哪些 AI 建议、审稿阶段提过什么修改意见，以及后面是怎么改的。如果需要进一步核实，把日志和投稿 PDF 拖进验证页，就能检查记录有没有被事后改动、对应的到底是不是这份投稿 PDF。至于作者参与得深不深，交由读者根据具体记录自己判断，而不是给一个武断的分数。

## 作者怎么用

1. **平时照常写。** Paperroom 会按时间顺序把已完成的关键动作记入「写作记录」，比如提交段落的逐句意图、采纳 AI 润色、保存正式版本、提交审阅意见等。日常敲键和没提交的草稿都不会记录。
2. **给项目开启可信时间戳。** 只需开启一次。之后每次保存带 PDF 的正式版本，Paperroom 都会自动向时间戳机构申请一份回执，把“截至这一版的日志指纹”和“这一版 PDF 的 SHA-256 指纹”一起封存起来。
   - 时间戳机构只会收到摘要，永远看不到你的论文和笔记内容。
   - 断网也不影响保存稿件，对应版本会先标为「待封存」；网络恢复后可以补盖，回执上显示机构实际签发的时间。
3. **投稿时按需导出。** 在「写作记录」里选中准备投稿的版本，点 **导出写作日志**。
   - 默认只导出事件摘要（时间、动作类型、对应章节/版本等），不包含具体正文和批注原文。
   - 你可以逐条勾选愿意公开的原文——例如某一条审阅意见和 AI 的回应——导出前可以预览审稿人最终会看到的画面。
   - 导出得到 `paperroom-log.json`，和封存的那一版 PDF 一起提交即可。

## 审稿人怎么看、怎么验

审稿人打开 Paperroom 的公开验证页，把 `paperroom-log.json` 拖进去就能直接阅读写作时间线；再把投稿 PDF 拖进去，就能核对稿件是否匹配。

整个页面完全在浏览器本地运行——**不用装插件、不用登录账号、也不会上传任何文件**。页面会自行重新计算校验结果，并在时间线上方逐项给出结论：

| 页面显示 | 审稿人可以据此确认什么 |
| --- | --- |
| **日志一致 · 共 90 条** | 所有公开的事件字段和先后顺序都未经篡改；展开已公开的原文时，也能核对原文与当初的指纹一致。 |
| **时间戳有效 · 已覆盖第 1–86 条** | 第三方可信时间戳机构证明，第 1–86 条记录的摘要最迟在签发时刻就已存在；第 87–90 条是封存之后新增的，尚未被这份回执覆盖。 |
| **投稿 PDF 匹配** | 拖入的 PDF 与该封存版本的 PDF 字节完全一致。只拖入日志时，此处显示「尚未核对 PDF」。 |

**审稿人实际看到的例子**（虚构内容）：展开「Method · 第 2 段」，可以看到作者先亲手提交了逐句意图，随后采纳了一次 AI 润色；到了 V2 审阅记录，作者公开了自己留的一条批注——「这句话把模拟器上的结果推广到了真实设备，请收窄结论」——展开下一版，还能看到 AI 是怎么回应并修改的。比起“作者一共保存过几次”，这种具体记录更能说明作者是如何主导修改的。

## “可校验”到底能证明什么，不能证明什么

- **事后删改一定会被发现。** 每条记录都链着上一条的指纹。只要对照投稿时留存的封存回执，事后改写、删除或调换其中任何一条，校验都会立刻报错。当然，如果有人只交一份较早的旧日志，验证页只能确认那份旧日志覆盖到的范围；作为核对基准的最终文件和日志，仍需由投稿系统或收件人留存。
- **把“本机时间”和“可信时间”分清楚。** 时间线里每步的操作时间来自作者本机（理论上可被修改），而第三方 [RFC 3161 时间戳](https://www.rfc-editor.org/rfc/rfc3161) 证明的是“截至某条记录，这段历史最迟在这个时间点就已经存在”。缺失证据时，页面会明确区分「尚无独立时间戳」「回执无法验证」「稿件不匹配」，让审稿人一眼看出缺的是哪一环。
- **公开到哪一层，就验到哪一层。** 给审稿人看的基本信息（事件类型、章节、版本等）都在封存范围内；每条私密原文都单独加随机盐生成指纹。作者勾选公开时，才会把对应原文和盐一起放进导出文件；没勾选的条目在页面上只显示「原文未披露」，既保护隐私，又不影响整条日志链的校验。
- **诚实说明证明边界。** 日志和第三方时间戳只证明**记录的完整性和存在时间**；具体是谁坐在电脑前敲的、作者实际思考了多久、人类贡献占百分之几，都超出了技术能证明的范围。

## 特殊情况怎么处理

| 常见情况 | 处理方式 |
| --- | --- |
| **论文写到一半才用上 Paperroom** | 日志会明确标出记录从哪里开始，接入前已有的正文作为起点，绝不补造之前的写作过程。 |
| **本地清理了旧 PDF（比如把原 V4 顺延显示为 V1）** | 封存记录绑定的是稳定的内部版本 ID 和 PDF 指纹。哪怕本地删掉了旧 PDF，审稿人手里只要有当初那份文件，依然可以核对通过。 |
| **从项目存档回滚后接着写** | 后续版本会标明是从哪份存档、哪一版继续的；之前已经发给收件人的旧日志依然可以独立校验。 |
| **导入旧版本导出的日志** | 保留旧格式的完整导出和校验能力。因为旧格式把原文和元数据混在一起算指纹，如果隐藏原文导致无法重算摘要，验证页会明确提示原因。 |

## 代码实现与校验方式

完整实现包含：选择性披露事件摘要链（[journal.py](../plugins/paperroom/runtime/journal.py)）、项目级自动封存与选择性导出（[timestamps.py](../plugins/paperroom/runtime/timestamps.py)、[tsa.py](../plugins/paperroom/runtime/tsa.py)）、浏览器纯本地验证页（[verify.html](verify.html)），以及命令行离线核验脚本（[verify_timestamps.py](../scripts/verify_timestamps.py)）。

**离线验收要点**：
1. **正常通过**：把导出的日志和对应 PDF 拖进验证页，日志一致、时间戳有效、PDF 匹配三项全部通过。
2. **篡改必报**：分别替换成另一份 PDF、改动一条已公开的批注、删掉一条已封存的中间事件，验证页都能准确指出具体哪一项失败。
3. **仅看日志**：只拖入 `paperroom-log.json` 时，时间线可正常阅读，PDF 项显示「尚未核对 PDF」。
4. **隐私有效**：不勾选批注原文时，导出的 JSON 里找不到任何批注原文，但整条日志的公开摘要和时间戳依然校验通过。
